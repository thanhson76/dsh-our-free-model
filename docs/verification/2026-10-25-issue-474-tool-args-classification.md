# Verification of Separating Syntactically Invalid Tool Arguments from Length Truncation

## Implementation

After a JSON.parse failure, `isTruncatedArguments` (channel pack `vendor/channel-pack/src/sse.ts`, the single source of truth, shared by the four adapters) performs an additional linear structural scan (string/escape state + `{[` depth): it judges truncation only when a string is unclosed or the bracket depth is non-zero; when the structure is complete and only the syntax is invalid (e.g. a bare value missing quotes, with the arguments ending in a closing `}`), it returns false, and the arguments go to tool-calls as they are, so the host's schema validation returns a clear error to the model for self-correction. The second confirmation in `src/stream.js`'s `brokenToolCall` is narrowed using the same judgment (with a new module-level `argumentsCutMidway`), so a structurally complete syntax error no longer downgrades the turn to max-tokens; `src/adapter.js` was not changed.

Two points added in self-review:

- **Non-zero depth rather than greater-than-zero**: a negative depth is the fragment-loss form of “the prefix is lost and only the middle and tail remain” (`"path.txt"}`, both double quotes present, the `{` lost) — imbalance in either direction belongs on the truncation recovery path that was measured to work. Judging only `> 0` would let that form slip into tool-calls.
- **`normalizeToolArguments` linkage**: its parse-failure branch previously fell back to `'{}'` unconditionally. After the judgment was narrowed, syntactically wrong arguments would fall into the normalize path and be forged into valid empty arguments — exactly the behaviour the comment in `sse.ts` forbids. It was changed to branch on the same structural judgment: incomplete → `'{}'` (the historical serialization path must produce valid JSON, keeping the old behaviour), syntax error → returned as-is.

## Boundaries

- No real upstream verification was done (the bare-value arguments in the issue are taken from the report's original text and used as regression literals); the host's actual behaviour in returning tool-calls + invalid arguments depends on DSH's existing schema validation path and was not accepted end-to-end inside native DSH.
- Expectation 3 in the issue (feeding the raw arguments from a parse failure back in as a prompt) was not implemented; it is a new recovery mechanism, and the planning document records the trade-off.
- Extra closing brackets (`{"a":1}}`) are placed under truncation via the negative depth (conservatively taking the retry path that was measured to work); if syntactically wrong arguments are stored by the host into the session as-is, the next round's history serialization will send them back upstream as-is, which may trigger an upstream 400 — that is the cost of “honestly passing on the error”, and it is better than forging empty arguments.
