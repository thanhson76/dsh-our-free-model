# v2.7.2 Plugin Release

This release is plugin-only; the desktop installer and standalone product versions remain as they were.

## Fixing the Legacy Upgrade Path

Previously the legacy upgrader accepted at most 80 files, each at most 4 MiB, while the 2.7.1 manifest had 93 files and included an engine of about 65 MiB. Whichever download source they switched to, legacy users failed while reading the manifest.

2.7.2 is based on the latest mainline: it merges the Token-saver module into a generated file, and gzip-compresses the engine before splitting it into 9 shards of no more than 4 MiB each. The plugin manifest totals 79 files, so legacy versions can upgrade directly, with no transitional version to install first. On its first start the engine reads only the local shards, verifies the digest of each shard, of the compressed body and of the final executable separately, and restores to a separate cache within the declared decompression limit; no code is fetched from the network to fill gaps.

The release build rejects content exceeding the legacy file-count or size budget. The historical upgrader regression fixtures are taken directly from the original Git objects of 1.3.1 and 2.5.9, with no legacy limit loosened. The runtime backup also completes the engine metadata and full binary, making rollback easier when a later upgrade fails.

## Latest Plugin Fixes Included

- Kilo and the anonymous free models are unified into the free pool, the tab counts and the five-cell status.
- The water level excludes rate-limited, unavailable, region-limited and hidden models. When 9 of 26 models are rate-limited, 17/26 is shown as 65%. Unprobed models are only candidates and do not masquerade as measured-available.
- Probing uses an independent upstream session per model, avoiding a whole round sharing a quota and causing bulk rate-limit misjudgements.

## Installation and Verification Boundaries

Self-installed legacy users can check and upgrade on the plugin upgrade page. Package-manager-managed installs continue to update the trusted tarball through the host, without bypassing the managed policy. For a manual install, use this release's full plugin package and keep the original user data directory; do not replace only the entry files.

Before release, the full contributor checks, production signing and the legacy upgrade regression must pass; see the PR and the release verification records for the concrete evidence. Verified legacy scenarios include download, installation, module loading, user data retention, rollback on activation failure, rejection of bad shards and Windows engine startup. The tests only access local services and do not mean every network environment or real model upstream has been verified.

## Rollback

When upgrade activation fails, the old package is restored automatically; if restoration meets a file-system error, the verified backup and the error evidence are kept and success is not reported. For a manual rollback, use the previous version's trusted plugin package and keep user configuration, accounts and statistics.
